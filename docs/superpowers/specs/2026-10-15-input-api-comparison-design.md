# 输入 API 对照实验设计

日期：2026-10-15。承接 `docs/single-macro-tail-and-end-to-end-2026-10-14.md` 的「下一步」与 `docs/superpowers/plans/2026-10-14-scheduling-latency-phases.md` 的遗留项。

## 目的与边界

调度器本身已到微秒级，端到端的毫秒级耗时集中在调度器之外：源按键到钩子入口约 0.46ms，钩子入口到 `CallNextHookEx` 返回约 0.87ms，钩子返回到目标 `WM_KEYDOWN` 约 2.9ms（Win32 自动组 P50）。本实验用同一把尺子比较**不同的用户态输入 API**，判断哪些值得在产品里单独设计接入。

范围内：触发捕获侧与注入侧的用户态 API 对照。
范围外，本轮不做：

- 产品代码的任何默认行为改动。实验只新增独立探针工具与文档。
- 驱动级注入（VHF、过滤驱动）。本轮出结果后，另建独立仓库研究，不放进本仓库。
- 绕过公开接口的直接系统调用；`PostMessage` 类后台输入（语义不同，不是同类对照）。

## 工具

新增 `src/tools/InputApiProbe`（.NET 8 Windows 控制台，含一个 Win32 接收子进程模式）。不改 `EndToEndProbe`，该工具与宏引擎和 WPF 接收端耦合较深，本实验不需要宏引擎。所有计时用 `Stopwatch.GetTimestamp()`（QPC），同机同时基，保留全部样本与异常值，分位数用 nearest-rank。

## 实验 A：触发捕获

测量量：`t_capture - t_send`，`t_send` 是发送端调用 `SendInput` 之前取的 QPC，`t_capture` 是各捕获方式回调或消息处理入口的第一个 QPC。携带专属 `dwExtraInfo` 标记的注入 F8 作为触发源。

候选：

| 编号 | 方式 | 备注 |
|---|---|---|
| A0 | `WH_KEYBOARD_LL`（基线，复用生产 `GlobalKeyboardHook` 源码） | 对照组，能吞键 |
| A1 | Raw Input：`RegisterRawInputDevices` + `RIDEV_INPUTSINK`，独立高优先级消息线程 | 不能吞键；先确认能否收到合成输入 |
| A2 | `RegisterHotKey` | 只支持修饰键+主键的标准组合；没有释放事件 |
| A3 | 专用线程轮询 `GetAsyncKeyState`，分别用 250µs 与 1ms 周期 | 记录 CPU 占用；可能漏掉很短的按键 |

先决检查：A1 与 A3 是否能看到 `SendInput` 产生的合成按键。看不到的候选，自动测试组排除并在结果中说明，只留物理按键组。

方法：

- **单独组（主结果）**：每次只启用一个候选。五轮，每轮对每个候选各 2,000 次触发，候选顺序每轮轮换。触发间隔 10ms，以免相互影响。
- **并列组（辅助）**：所有候选同时启用，同一次按键，比较各自到达的先后差。启用多个候选会互相拖慢，所以只用于物理按键 30 次的相对先后，不与单独组的绝对值混用。
- 每个候选独立报告 N、P50、P95、P99、P99.9、max、丢失与重复次数。

## 实验 B：注入到接收

测量量：`t_receive - t_send_begin`，接收端为独立进程的原生 Win32 `GetMessage` 窗口，记录前台时 `WM_KEYDOWN` 的 QPC。发送端自己不安装钩子，除非该组变量要求。

候选：

| 编号 | 方式 |
|---|---|
| B0 | `SendInput`，虚拟键码（基线，对应现有生产路径） |
| B1 | `SendInput`，`KEYEVENTF_SCANCODE` |
| B2 | `SendInput`，虚拟键码加扫描码 |
| B3 | `keybd_event` |
| B4 | `SendInput` 按下+抬起合并为一次调用，与分两次调用对比（按下和抬起之间的间隔也一并记录） |

附加因子：发送进程内是否同时安装 `WH_KEYBOARD_LL` 空钩子（只调用 `CallNextHookEx`）。用来量化「钩子税」：钩子入口到返回约 0.87ms 是否由系统路由中的钩子本身引入，而不是目标慢。

方法：每个候选五轮，每轮 2,000 次，顺序轮换，因子在每个候选内交替。接收端校验次数，不把 `SendInput` 返回值当作接收。失焦或缺失接收则中止并保留记录。

## 输出与判定

- 原始 CSV：`tmp/input-api-20261015/`，含每次的 QPC 字段、候选编号、轮次、因子。
- 汇总脚本沿用 `scripts/summarize_end_to_end.py` 的统计口径，新增 `scripts/summarize_input_api.py`。
- 结果文档：`docs/input-api-comparison-2026-10-15.md`，同步更新 `docs/current-precision-status.md` 的指针。文档保留未通过和更差的候选，说明机器、系统版本和负载状态。
- 语义兼容表（写入结果文档）：是否能吞键、是否能区分注入与物理、释放事件、鼠标键、修饰键组合、是否需要消息泵。

判定门槛，满足才进入「值得接入」名单，之后单独设计：

1. 相比基线，P50 改善不少于 100µs，且 P99 与 max 没有变差；
2. 五轮中至少四轮方向一致；
3. 语义兼容表中没有生产必须的功能缺失（尤其是吞键），或者可以与现有路径并用来补足。

否则记为「无净收益」，不接入。机器底噪太大无法分辨的，写明「无结论」，不硬下结论。

## 风险与注意

- 合成输入的处理路径与物理键盘不完全相同，实验 A 的绝对值只适合候选之间比较，不代表物理键盘到回调的延迟。
- 轮询方案会占 CPU，需在结果里同时给出 CPU 时间。
- 测量期间不得同时构建或跑其他基准；同一环境、电源方案与 Turbo 设置，记录在 provenance 文件里。
- 实验结果不构成对游戏内输入延迟的承诺。游戏帧时间与真实游戏消费仍需另测。
